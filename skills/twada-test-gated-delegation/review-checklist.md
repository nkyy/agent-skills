# テストのレビュー項目

エージェントが書いたテストを `test:` でコミットする前に確かめる。各項目は「見つけたらどうするか」まで決めておく。

| 確認すること | 確かめ方 | 見つけたら |
|---|---|---|
| 各テストがテストリストのどの項目に対応するか | テスト名・コメントとリストを突き合わせる | リストにないテストは差し戻す |
| 自分で実行して全件の Red/Green が報告と一致するか | テストを実行し直す | 不一致なら差し戻す |
| テストファイルが静的解析（clippy 等）を通るか | 実装段階と同じ設定（`--all-targets -D warnings` など）でかける | テストのコミット前に直す（実装段階で、変更禁止のテストのせいで止まるのを防ぐ） |
| 今の実装に対して通るテストの理由 | 新しい振る舞いか、既存振る舞いの回帰防止かを分ける | 前者なら弱いテストとして補強 |
| 前提状態を内部形式の手書きで作っていないか | `catalog.json` 等の内部ファイルを書いている箇所を grep | 公開 CLI／API で作り直させる |
| skip・early return・許可リストで素通りする経路 | `return`、`skip`、許可用の環境変数の扱いを読む | 既定で失敗する形に直す |
| 未実装を「未検証」扱いしていないか | 未検証の理由が「環境の制約」か「実装がまだない」か | 後者は普通の assert に直す |
| 「起きないこと」テストに実害の根拠があるか | 「壊れたら誰がどう困るか」がリストに書かれているか | なければ削除 |
| スキーマや期待値が仕様から起こされているか | 仕様の該当節と1項目ずつ照合する | 根拠のない項目を外す |
| 新しい契約を、古いテストの例に合わせて弱めていないか | スキーマで「任意」になった項目と、その理由（「既存の例を保つため」など）を確かめる | 契約を必須にし、古い例のほうを新しい契約に合わせる |
| 外部契約の命名が仕様どおりか | ファイル名・接頭辞（例: `o_`）・理由コード | 仕様に合わせる |
| 補強したテストが本当に強いか | 旧テストがすり抜けた実装・コミットに新テストをかける | 落ちなければ再補強 |

## 前提待ちの Red の限界

テストが前提の段階（未実装のコマンドなど）で落ちている間は、**その先のアサーションは一度も実行されていない**。誤り（パスの正規化漏れ、比較対象の取り違えなど）はレビューでは見つけにくく、実装段階で初めて表に出る。

- 実装中のエージェントには「テストがおかしいと思ったら、直さずに止まって報告する」を必ず指示する。
- 報告を受けたら、レビュー担当が原因を確かめてテストだけを直し、`test:` でコミットしてから実装を再開させる。実装側の未コミット差分には触れない。

**コミットはテストの終了コードで止める。**「テストを実行して `grep` で結果を表示し、そのままコミット」とつなぐと、`grep` が成功を返すのでテストが落ちてもコミットされる。`cargo test --no-fail-fast && git commit ...` のように、テストのコマンド自体の成否でつなぐ。

軽微な修正（数行）はレビュー担当が直してよい。直した内容はコミット本文に記録する。
