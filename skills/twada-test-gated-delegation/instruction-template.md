# 指示書のひな形

コーディングエージェントに渡す指示書の骨組み。段階ごとに1枚作り、リポジトリの `docs/milestones/` に置いてコミットしてから渡す。

## A. テストだけを書かせる段階

```markdown
# 指示書 <ID>: <項目> のテストを書く（テストだけ。実装しない。コミットしない）

## 読むもの（この順。矛盾したら後者が優先）
1. 仕様本体 → 2. 仕様の補足（新しい順に優先）→ 3. テストリストの対象項目 → 4. 既存テスト

## やること
- 対象項目 Tn ごとにテスト関数を1つ書く。ビルドした成果物を外から実行する。
- 前提状態は公開 CLI／API で作る。仕様・ADR で定めた部分だけを変えてよい。

## Red の確認
- 全テストを実行し、テストごとに「どこで落ちたか」（前提待ちか、自分の期待か）を報告する。
- 今の実装に対して通ってしまうテストがあれば、新しい振る舞いを確かめているか見直し、報告する。

## 禁止事項（性質と手段の対）
- 前提を作るために、内部ファイルの中身や内部構造を手書きしない（仕様にない形式に縛られる）。
- 環境で再現できない前提を、early return や skip で合格にしない。既定で失敗させ、明示許可した場合だけ UNVERIFIED を出す。
- 未実装による失敗を「未検証」の仕組みで扱わない。
- スコープ上の制約（〜が存在しないこと）をテストにしない。
- 拒否を確かめるテストの「正しい入力なら成功する」対照は、**そのテストが確かめるコマンドだけ**に絞る（後の項目の機能まで対照に入れると、実装の順番どおりに緑にできなくなる）。
- 実装コードを変更しない。コミットしない。

## 完了報告
1. 追加したテストと確かめていること  2. テストごとの失敗箇所  3. 今の実装で通ったテストと理由
```

## B. 実装させる段階

```markdown
# 指示書 <ID>: <項目> を実装する

## 進め方
対象 Tn を順に、最小の実装 → 全テスト実行 → `feat: Tn <要約>`（本文に新しく緑になったテスト）→ 必要なら `refactor:`。

## してはいけないこと
- 後の項目のテストを緑にする実装を先に書かない。避けられない場合はコミット本文に理由を書く。
- テストファイル・スキーマを変更しない。おかしいと思ったら止まって報告する。
- テストのない振る舞いを実装しない。
- 仕様の禁止事項（例: 自動修復、自動移行）を具体的に列挙する。

## テストのない仕様上の必須事項
そのコードを初めて書く feat の中でだけ入れてよい。後の項目のテストを緑にしてはならない。コミット本文に列挙する。

## コミット
- `feat`・`fix`・`refactor`・`perf`・`test` のコミットは、本文に Why（なぜ変えたか）を書く。件名だけで済ませない（`how-what-why-whynot`）。
- 指示書を通さずに単発で頼むときも、この1行を必ず添える。

## git
`git add` / `git commit` が権限エラーで失敗したら、単独のコマンドで最大2回まで再試行し、だめなら止まって報告する。

## 完了報告
1. 項目ごとの状態と新しく緑になったテスト  2. 先行 Green とその理由  3. コミット一覧  4. 最終のテスト・静的解析結果  5. 止まった箇所
```
